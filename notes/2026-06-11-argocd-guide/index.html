Argo CDをエンジニア向けに理解する

Argo CDは、Gitに記述された望ましい状態とKubernetesクラスタの実状態を継続的に比較し、差分を可視化・同期するGitOps型のContinuous Deliveryツールです。

30秒でわかる答え

Argo CDは「GitのこのコミットどおりにKubernetesを保つ」コントローラーです。Gitへの変更を検知してデプロイし、クラスタ上の手作業変更も差分として検出します。CIがクラスタへ直接pushするのではなく、Argo CDがGitから望ましい状態をpullして継続的に収束させます。

Argo CDとGitOps

GitOpsでは、アプリケーションと環境の望ましい状態を宣言的な設定としてGitで管理します。変更はPull Requestでレビューされ、Gitの履歴が「いつ・誰が・何を変えたか」の監査証跡になります。

中心概念: Reconciliation

Argo CDはKubernetes Controllerとして動作し、Gitの望ましい状態とクラスタの実状態を繰り返し比較します。この制御ループをreconciliationと呼びます。

Desired State
Git上のManifest
Compare & Sync
差分検出・反映
Live State
Kubernetesクラスタ
  • Synced: Gitとクラスタの状態が一致している。
  • OutOfSync: Gitとクラスタに差分がある。
  • Healthy: Deploymentなどが期待どおり稼働している。
  • Degraded: リソースが失敗・異常状態にある。

SyncedでもPodが起動失敗していればDegradedになり得ます。同期状態とヘルス状態は別の軸です。

Applicationリソース

Argo CDでは、どのGitリポジトリの何を、どのクラスタ・NamespaceへデプロイするかをApplicationカスタムリソースで宣言します。

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: sample-api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/platform-config.git
    targetRevision: main
    path: environments/production/sample-api
  destination:
    server: https://kubernetes.default.svc
    namespace: sample-api
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
設定意味
sourceGitリポジトリ、リビジョン、Manifestのパス
destinationデプロイ先クラスタとNamespace
project許可するリポジトリ、クラスタ、リソース種別などの境界
automated差分を自動同期するか
pruneGitから削除された管理対象リソースをクラスタからも削除するか
selfHealクラスタ側で変更された状態をGitの状態へ戻すか

Manifestの管理方法

Argo CDはプレーンなYAML/JSONだけでなく、Helm、Kustomize、Jsonnet、Config Management Pluginなどを扱えます。

方式向いている場面注意点
Plain YAML小規模で単純な構成環境差分で重複しやすい
Kustomize共通baseへ環境差分を重ねるoverlayの複雑化に注意
Helm再利用可能なchartとvaluesで管理するテンプレート結果がGit上で直接見えにくい
Plugin独自生成ツールやSecret連携実行コードの信頼境界と保守が増える

典型的なデプロイフロー

  1. 開発者がアプリケーションコードを変更する。
  2. CIがテストを行い、コンテナイメージをビルド・Registryへpushする。
  3. CIまたは別の自動化がGitOpsリポジトリのイメージタグを更新し、Pull Requestを作る。
  4. レビュー後にGitOpsリポジトリへマージする。
  5. Argo CDが差分を検出し、手動または自動でクラスタへ同期する。
  6. Argo CDが同期状態とリソースのヘルスを監視する。
責務の分離

CIはテストと成果物作成、Argo CDは望ましい状態のデプロイと継続監視を担当します。CIから直接kubectl applyする必要がなくなります。

同期戦略

手動同期

Gitとの差分を確認し、人間がSyncを実行します。本番導入初期や、厳格な変更承認が必要な環境で理解しやすい方法です。

自動同期

Gitの変更を検知すると自動で同期します。Gitへのマージをデプロイ承認として扱えるため、CIからArgo CD APIを呼ぶ必要がありません。

PruneとSelf Heal

  • Prune: Gitから消えたリソースをクラスタから削除する。便利だが削除事故の影響が大きい。
  • Self Heal: kubectl editなどで生じたdriftをGitの状態へ戻す。

本番で自動同期・Prune・Self Healを有効にする場合、Pull Requestレビュー、保護ブランチ、AppProject、Sync Window、通知、復旧手順を組み合わせます。

適用順序: Hooks・Phases・Waves

複数リソースの適用順序や、デプロイ前後の処理はSync Phases、Resource Hooks、Sync Wavesで制御できます。

仕組み用途例
PreSync Hookデプロイ前のDBマイグレーションや検証Job
Sync通常のManifest適用
PostSync Hookデプロイ後のスモークテストや通知
SyncFail Hook同期失敗時の通知や後処理
Sync WaveNamespace、CRD、アプリのように適用順序を数値で指定

順序制御を増やしすぎると、宣言的な構成が暗黙の手順書へ変わります。依存関係を減らし、失敗時に再実行可能な処理へすることが重要です。

ApplicationSetと複数環境

ApplicationSetは、テンプレートとGeneratorから複数のApplicationを生成します。クラスタごと、環境ごと、Gitディレクトリごとに同じアプリを展開する場合に有効です。

Generator
cluster・Git・listなど
ApplicationSet
Applicationをテンプレート生成
複数クラスタ・環境へ
一貫してデプロイ

ApplicationSetは大規模運用を簡潔にしますが、テンプレートの誤りが多数環境へ波及します。対象選択条件、変更レビュー、段階的展開を慎重に設計します。

アプリコードとGitOps設定を同じリポジトリに置く方法、別リポジトリに分ける方法の両方があります。別リポジトリにすると、アプリの変更とデプロイ承認、アクセス権限、監査境界を分離しやすくなります。

Secret管理

Gitを正解にしても、平文のSecretをGitへ保存してはいけません。Argo CD自体は汎用Secret管理システムではないため、組織の要件に合わせて別の仕組みを組み合わせます。

  • External Secrets Operatorなどで外部Secret Managerから同期する。
  • Sealed SecretsやSOPSなどで暗号化した値をGit管理する。
  • Config Management Pluginを使う場合、Repository Serverで実行するコードと権限を厳格に管理する。
  • Argo CDが利用するGit・クラスタ資格情報を最小権限にする。

設計・運用で重要な点

  • AppProjectで境界を作る: チームごとに許可リポジトリ、宛先クラスタ、Namespace、リソース種別を制限する。
  • Gitへの直接変更を防ぐ: 保護ブランチ、レビュー、署名、CI検証を導入する。
  • 手作業変更を原則禁止する: 緊急変更を行った場合も、すぐGitへ反映してdriftを解消する。
  • タグを固定する: 本番ではlatestを避け、イメージdigestや不変タグで再現性を確保する。
  • 差分を理解する: mutating webhookやcontrollerが変更するフィールドは、安易にignoreせず原因を把握する。
  • 通知と監視を整備する:同期失敗、Degraded、OutOfSyncの長期化を検知する。
  • Argo CD自体を保護する: SSO、RBAC、TLS、ネットワーク制限、バックアップ、アップグレード手順を整える。

よくある失敗

失敗問題改善
Argo CD導入後もCIから直接applyする正解の経路が複数になり、driftや競合が発生するデプロイ経路をGit経由へ統一する
Gitへ平文Secretを置く履歴に資格情報が永続化する外部Secret管理や暗号化を使う
全チームへ管理者権限を与える誤操作・侵害時の影響範囲が広いAppProjectとRBACで最小権限にする
最初から全環境で自動PruneするGitの誤削除が即座に本番へ反映される段階導入とレビュー・保護策を設ける
OutOfSyncをすべてignoreする本来検知すべきdriftを隠す差分の発生源を特定して限定的に設定する

Argo CDが向いているケース

  • Kubernetes上の複数アプリ・環境・クラスタを一貫して管理したい。
  • Pull RequestレビューとGit履歴をデプロイ監査へ利用したい。
  • クラスタのdriftを検出・修復したい。
  • 開発チームへセルフサービスなデプロイ体験を提供しつつ、権限境界を保ちたい。

慎重に判断するケース

  • Kubernetesを使っていない、または対象がごく小規模。
  • Git上で宣言できない手続き的なデプロイが中心。
  • GitOpsリポジトリ、権限、Secret、監視を運用する体制がない。
理解の要点

Argo CDは単なるデプロイボタンではなく、Gitの宣言とクラスタの実状態を継続的に一致させるコントローラーです。導入効果は、Gitを本当に唯一の正解として運用できるかで決まります。

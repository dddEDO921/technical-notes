JavaScriptのベストプラクティスとアンチパターン

読みやすい構文集ではなく、変更時の事故、非同期の競合、性能劣化、セキュリティ問題を減らすための設計判断を、良い例と悪い例で整理します。

30秒でわかる答え

良いJavaScript実装は、状態・依存・副作用・失敗条件が見えるコードです。アンチパターンは、短期的には便利でも、それらを暗黙化して変更影響を読めなくします。ベストプラクティスは絶対規則ではなく、要件・対象環境・計測結果に合わせて選びます。

「ベストエフォート」と「ベストプラクティス」

一般に実装指針を指す言葉はベストプラクティスです。ベストエフォートは「可能な範囲で最大限努力するが、結果は保証しない」という意味で、通信品質やサービス提供条件などで使われます。

ただし、ベストプラクティスも万能な正解ではありません。チームの規模、製品寿命、対象ブラウザ、性能要件、障害時の影響によって適切な選択は変わります。

1. 状態と依存関係

推奨: 状態の所有者と更新経路を1つにする

export function createCart() {
  let items = [];

  return {
    getItems: () => structuredClone(items),
    addItem: (item) => {
      items = [...items, item];
    },
  };
}

状態を更新できる場所を限定し、外部へはコピーまたは読み取り専用の表現を返します。どこからでも直接変更できる状態は、変更原因を追いにくくします。

アンチパターン: グローバルな可変状態

// どのファイルからでも変更できる
window.appState = {
  currentUser: null,
  cart: [],
  loading: false,
};

テスト間で状態が漏れ、実行順依存や競合が生まれます。共有が必要な場合でも、更新API、寿命、初期化方法、監視方法を明示します。

アンチパターン: Boolean引数だらけの関数

// 呼び出し側で意味が分からない
renderUser(user, true, false, true);

// 意図が分かる
renderUser(user, {
  showAvatar: true,
  editable: false,
  showActions: true,
});

引数が増えたら設定オブジェクトや責務分割を検討します。ただし、小さな関数へ過剰な抽象化を追加しないことも重要です。

2. 関数とモジュール設計

推奨: ビジネスルールと副作用を分ける

export function calculateDiscount(order) {
  return order.total >= 10_000 ? order.total * 0.1 : 0;
}

export async function saveOrder(order, repository) {
  const discount = calculateDiscount(order);
  return repository.save({ ...order, discount });
}

計算ロジックは純粋関数としてテストし、通信や保存は境界へ寄せます。依存を引数で受け取ると、差し替えとテストが容易になります。

アンチパターン: 巨大な万能関数

async function submitOrder() {
  // DOM取得、入力検証、金額計算、API通信、
  // Storage更新、画面遷移、通知、ログ送信をすべて行う
}

行数だけで分割するのではなく、変更理由が異なる処理を分けます。小さな関数を多数呼んでも、同じタスク内で重い処理をすれば性能は改善しない点にも注意します。

アンチパターン: 早すぎる共通化

似ている2つの処理をすぐ共通化すると、後から異なる要件を大量の条件分岐で吸収することになります。重複の意味と変化方向が分かってから抽象化します。

3. 非同期処理

推奨: Promiseの所有者と失敗処理を明確にする

async function loadProfile(id, { signal }) {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`, { signal });

  if (!response.ok) {
    throw new Error(`Profile request failed: ${response.status}`);
  }

  return response.json();
}

呼び出し側は、成功、ユーザー向けエラー、キャンセル、再試行のどれを担当するか決めます。fetch()はHTTPエラーだけではrejectしないため、ステータス確認が必要です。

アンチパターン: Floating Promise

// 完了も失敗も待たれない
saveSettings();
navigateToHome();

Promiseを返す処理を待たない場合、失敗が見えず、処理順も保証できません。意図的なバックグラウンド処理なら、失敗の記録方法を決めたうえで明示します。

void sendAnalytics(event).catch(reportError);

アンチパターン: forEach(async ...)

// forEachは各Promiseを待たない
items.forEach(async (item) => {
  await saveItem(item);
});

// 順番に処理する
for (const item of items) {
  await saveItem(item);
}

// 独立しており、同時実行してよい
await Promise.all(items.map(saveItem));

直列・並列・同時実行数制限のどれが必要か、API負荷や処理順の要件から選びます。

アンチパターン: 古いリクエストの結果で上書きする

検索や画面遷移では、先に開始した処理が後から完了する競合が起きます。AbortControllerで不要な処理を止めるか、リクエストIDで最新結果だけを反映します。

4. エラーハンドリング

推奨: 回復できる場所で処理する

try {
  const user = await loadUser(id);
  renderUser(user);
} catch (error) {
  reportError(error);
  renderError("ユーザー情報を取得できませんでした");
}

低レイヤーは意味のある文脈を付けてthrowし、UI境界やジョブ境界など、回復方針を決められる場所で処理します。

アンチパターン: 例外を握りつぶす

try {
  await saveOrder(order);
} catch {
  // 何もしない
}

利用者には成功したように見え、監視にも残りません。無視してよい例外なら、なぜ安全かを明確にし、必要に応じて記録します。

アンチパターン: すべてを例外にする

ユーザーの入力不足や検索結果0件など、想定内の結果まで例外にすると制御フローが読みにくくなります。期待される分岐は結果型や明示的な戻り値で表し、予期しない失敗と区別します。

5. DOMとセキュリティ

推奨: 外部入力をデータとして扱う

const message = document.createElement("p");
message.textContent = apiResponse.message;
container.replaceChildren(message);

アンチパターン: 外部入力をHTMLとして実行可能にする

// XSSにつながる
container.innerHTML = apiResponse.message;

HTMLを許可する要件がある場合は、許可範囲を限定し、実績あるサニタイザー、Content Security Policy、Trusted Typesなどを使います。自作の文字列置換だけでHTMLを安全化しないでください。

アンチパターン: インラインイベントとeval()

<button onclick="deleteItem('123')">削除</button>

eval(userProvidedCode);

HTMLと動作が密結合になり、CSP導入や静的解析を難しくします。イベントはaddEventListener()で登録し、文字列をコードとして実行しません。

6. 性能

推奨: 送る量と実行する量を減らす

  • 初期表示に不要な機能はdynamic importで遅延読み込みする。
  • HTMLやCSSで解決できる機能をJavaScriptで再実装しない。
  • 重い処理は計測し、必要に応じて分割、遅延、Web Workerへの移動を行う。
  • イベントハンドラ内では、利用者へ必要な反応を先に表示する。

アンチパターン: 長い同期処理でメインスレッドを塞ぐ

ブラウザのメインスレッドは基本的に1度に1つのタスクを処理します。50msを超えるタスクはlong taskとして扱われ、入力への応答を遅らせます。処理量を減らし、必要ならタスクを分割します。

アンチパターン: レイアウトスラッシング

// 読み取りと書き込みを交互に行い、再レイアウトを繰り返す
items.forEach((item) => {
  const height = item.offsetHeight;
  item.style.height = `${height + 10}px`;
});

DOMの読み取りをまとめ、その後に書き込みをまとめます。ただし、最適化前にPerformance panelなどでボトルネックを確認します。

アンチパターン: 推測によるマイクロ最適化

可読性を犠牲にした小さな高速化より、不要な通信、巨大な依存、長いタスク、過剰なDOM更新を先に改善します。性能判断には実ユーザー環境の計測が必要です。

7. データとAPI境界

推奨: 外部入力を実行時に検証する

function parseUser(value) {
  if (
    typeof value !== "object" ||
    value === null ||
    typeof value.id !== "string" ||
    typeof value.name !== "string"
  ) {
    throw new TypeError("Invalid user response");
  }

  return value;
}

TypeScriptの型は実行時には消えます。API、Storage、URL、フォーム、postMessageなど、信頼境界を越える値は実行時に検証します。

アンチパターン: JSONの形を無条件に信頼する

const user = await response.json();
renderUser(user.profile.name);

API変更や異常データで深い場所から例外が発生し、原因が分かりにくくなります。境界で検証し、内部では検証済みデータを扱います。

8. テストと保守

推奨: 契約と重要な振る舞いをテストする

  • 純粋関数は入力・出力と境界値をUnit Testで確認する。
  • 通信・DOM・Storageとの連携はIntegration Testで確認する。
  • 重要なユーザーフローはE2E Testで確認する。
  • Formatter、Lint、型チェック、テストをCIで実行する。

アンチパターン: 実装詳細だけを固定するテスト

内部関数の呼び出し回数やDOM構造の細部だけに依存すると、安全なリファクタリングでもテストが壊れます。利用者から見える振る舞いと公開契約を優先します。

アンチパターン: テストしにくさを放置する

テストが困難なのは、巨大な副作用、暗黙依存、責務混在の兆候であることが多いです。モックを大量に増やす前に設計境界を見直します。

レビューで使える質問

実務上の結論

最も危険なアンチパターンは、コードが動くことだけを確認し、失敗時・変更時・負荷時の振る舞いを設計しないことです。ベストプラクティスは、暗黙のものを明示し、問題を小さい境界で検出できるようにするために使います。

AIシステムをレイヤーで見る

AIシステムを「LLMアプリ」として見るのではなく、普通のWebアプリにAI層と検索層が追加されたものとして分解する。エンジニアにとって、この見方が一番実装・設計・運用に使いやすい。

30秒でわかる答え

LLMは中心に見えますが、実際には一部品です。AIシステムの品質は、LLM単体ではなく、UI、会話管理、権限制御、RAG、業務API、データ、監視、評価、人間の確認をどう接続するかで決まります。

一番大事な理解

AIシステムでは、LLMは中心に見えます。しかし、実際には次のような部品の1つです。

LLM:
  考える・文章化する・分類する

RAG:
  必要な情報を探す

Tool Calling:
  外部API操作につなげる

アプリ:
  全体制御、権限、検証、ログを担当する

人間:
  目的設定、確認、責任を持つ

LLMに全部やらせる設計は危険です。何を実行してよいか、どの情報へアクセスしてよいか、出力を信じてよいか、実行結果をどう記録するかは、アプリケーション層と運用層が制御します。

処理の流れ

  1. ユーザーがUIから依頼する。
  2. アプリケーション層がユーザー、権限、会話履歴、目的を確認する。
  3. 必要なら検索層が文書やDBから関連情報を取得する。
  4. アプリケーション層がプロンプトを組み立て、AI層へ渡す。
  5. AI層が回答、分類、次に呼ぶツール候補を生成する。
  6. Tool Callingが必要な場合、アプリケーション層が権限と引数を検証する。
  7. 業務API層が実際の登録・更新・検索を行う。
  8. 結果をデータ層へ保存し、監査ログとメトリクスを運用層へ送る。
  9. UIで結果や確認事項をユーザーへ返す。

LLMの役割

LLMは、自然言語を扱う強力な処理部品です。

  • ユーザーの依頼を解釈する。
  • 文章を生成・要約・分類する。
  • 非構造データを構造化する。
  • 次に呼ぶべきツール候補を提案する。
  • 検索結果やAPI結果を人間向けに説明する。

一方で、LLMは業務データの正本ではありません。最新情報、権限、状態変更、監査証跡は、外部データとアプリケーション側で管理します。

RAGの役割

RAGは、LLMの外にある情報を検索し、回答の材料として渡す仕組みです。社内文書、FAQ、仕様書、過去ログ、ナレッジベースなどを扱うときに使います。

検索方式向いているもの注意点
ベクトル検索意味が近い文書を探す似ているが正しくない文書を拾うことがある
全文検索固有名詞、ID、正確なキーワード表現ゆれに弱い
ハイブリッド検索意味検索とキーワード検索の両立スコア調整やリランキングが必要
構造化DB検索権限、金額、ステータスなど正確な条件自然文から安全なクエリへ変換する必要がある

RAGを入れても hallucination がゼロになるわけではありません。検索結果の品質、引用、根拠表示、回答できない場合の扱いが重要です。

Tool Callingの役割

Tool Callingは、LLMの判断を外部API操作へつなげる仕組みです。ただし、LLMが直接DBやAPIを自由に操作するのではなく、アプリケーション層が許可されたツールだけを実行します。

ユーザー:
  明日の10時に田中さんとの打ち合わせを入れて

LLM:
  schedule.create_event を呼ぶ必要があると判断

アプリ:
  ユーザー権限、参加者、日時、確認要否を検証

業務API:
  カレンダーに予定を作成

運用:
  誰が何を作成したか監査ログに記録

Tool Callingでアプリ側がやること

  • 呼び出し可能なツールを用途ごとに制限する。
  • 引数をスキーマで検証する。
  • ユーザー権限を確認する。
  • 重要操作は実行前に人間へ確認する。
  • 実行結果と失敗理由をログに残す。
  • 再試行してよい操作と、してはいけない操作を分ける。

レイヤーごとの壊れ方

レイヤーよくある失敗対策
UI層ユーザーがAIの出力を確定結果と誤解する根拠、確認状態、未確定状態を表示する
アプリケーション層権限制御や入力検証をLLM任せにする権限、スキーマ、実行可否をコードで制御する
AI層もっともらしい誤回答を返すRAG、引用、評価、回答不能時のルールを入れる
検索層関係ない文書や古い文書を取得するメタデータ、権限フィルタ、再ランキング、鮮度管理を入れる
業務API層誤った操作を実行する確認画面、トランザクション、冪等性、監査ログを用意する
データ層権限のない情報を検索・回答に混ぜるドキュメント単位・行単位のアクセス制御を検索前に適用する
運用層品質・コスト・失敗率が見えないログ、トレース、評価データ、コスト上限、アラートを整える

設計時のチェックリスト

  • LLMに何を任せ、何を任せないかを決めたか。
  • RAGで検索する文書に権限フィルタをかけているか。
  • 検索結果の根拠や引用をUIに表示するか。
  • Tool Callingの引数をスキーマで検証しているか。
  • 重要操作の前に人間確認を入れているか。
  • 業務APIの操作は冪等性・トランザクション・監査ログを考慮しているか。
  • プロンプト、検索結果、ツール呼び出し、最終出力を追跡できるか。
  • 評価データセットを作り、モデル変更やプロンプト変更の影響を測れるか。
  • トークン利用量、検索コスト、API実行回数に上限を設けているか。

普通のWebアプリとの違い

普通のWebアプリAIシステム
入力はフォームやボタンで構造化される自然言語入力を解釈する必要がある
処理結果はコードで決まるLLMの非決定的な出力が混ざる
DBやAPIが主な情報源文書検索、Embedding、会話履歴も情報源になる
テストは入力と期待出力を比較しやすい評価、サンプル会話、根拠一致、失敗率を見る必要がある
ログはAPI・DB操作中心プロンプト、検索、ツール呼び出し、モデル応答も追跡対象
実務上の結論

AIシステムの設計で大事なのは、LLMを賢い中心として扱うことではありません。LLMを不確実な部品として扱い、検索・権限・検証・業務実行・監査・人間確認をレイヤーごとに分離することです。

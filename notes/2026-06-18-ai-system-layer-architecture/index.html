AIシステムをレイヤーで見る

AIシステムは「LLMが中心の特別なアプリ」ではなく、普通のWebアプリにAI層と検索層が追加されたものとして見ると設計しやすい。

一番大事な理解

LLMは重要ですが、システム全体から見ると一部品です。品質と安全性は、LLM単体ではなく、UI、アプリケーション制御、RAG、Tool Calling、業務API、データ、運用、人間確認をどう分けて接続するかで決まります。

1. 全体像

普通のWebアプリに、AI層と検索層が追加されたイメージです。アプリケーション層が司令塔になり、LLM・検索・業務APIを直接つなげず、権限・検証・ログを通して制御します。

2. レイヤーごとの責務

レイヤー担当すること実装例責任を持たないこと
UI層入力、確認、結果表示Chat UI、フォーム、引用表示、確認ダイアログ権限判断や業務実行
アプリケーション層全体制御、会話管理、プロンプト生成、権限制御、ログBackend API、オーケストレーター、ポリシー判定LLM任せの実行判断
AI層解釈、生成、分類、要約、ツール候補生成LLM、Embedding、画像生成、音声認識正本データ保持や最終責任
検索層根拠を探してAIへ渡すRAG、ベクトルDB、全文検索、リランキング検索結果の無条件な正しさ保証
業務API層実際の業務処理を行う経費登録、予定作成、問い合わせ登録、チケット作成自然言語解釈
データ層正本データ、文書、ログ、権限情報を持つDB、文書、監査ログ、権限テーブルAIの推論
運用層監視、評価、監査、コスト管理メトリクス、トレース、Evals、アラート個別リクエストの業務判断

3. 主要部品の関係

LLM

考える、文章化する、分類する、要約する、ツール候補を出す。業務データの正本や権限判断は持たない。

RAG

必要な文書やナレッジを探す。検索品質、権限フィルタ、鮮度管理、引用表示が重要。

Tool Calling

外部API操作につなげる。実行可否、引数検証、確認、監査はアプリケーション層で行う。

部品得意なこと注意点
LLM自然言語の解釈、回答生成、分類、非構造データの構造化もっともらしい誤回答を返すことがある
RAG社内文書、FAQ、仕様書、過去ログから根拠を探す似ているが正しくない文書、古い文書、権限外文書を拾う危険がある
Tool Calling予定作成、経費登録、問い合わせ登録など外部操作へつなげる重要操作は人間確認、スキーマ検証、監査ログが必要
アプリ全体制御、権限、検証、ログ、失敗時の扱いここを薄くしすぎるとLLM任せの危険な設計になる
人間目的設定、確認、責任、最終判断責任をAIへ移譲したように見せない

4. リクエスト処理の流れ

  1. ユーザーがUIから依頼する。
  2. アプリケーション層がユーザー、権限、会話履歴、目的を確認する。
  3. 必要なら検索層が文書やDBから関連情報を取得する。
  4. アプリケーション層がプロンプトを組み立て、AI層へ渡す。
  5. AI層が回答、分類、または呼ぶべきツール候補を生成する。
  6. Tool Callingが必要な場合、アプリケーション層が権限と引数を検証する。
  7. 業務API層が登録・更新・検索などの処理を行う。
  8. 結果、検索根拠、ツール呼び出し、監査ログを記録する。
  9. UIで結果、根拠、確認事項をユーザーへ返す。
ユーザー:
  明日の10時に田中さんとの打ち合わせを入れて

LLM:
  schedule.create_event を呼ぶ必要があると判断

アプリ:
  ユーザー権限、参加者、日時、確認要否を検証

業務API:
  カレンダーに予定を作成

運用:
  誰が何を作成したか監査ログに記録

5. 検索層の考え方

RAGは「LLMに知識を足す魔法」ではなく、LLMの外にある情報を探して材料として渡す仕組みです。検索品質と権限制御が弱いと、回答品質も安全性も崩れます。

検索方式向いているもの注意点
ベクトル検索意味が近い文書を探す似ているが正しくない文書を拾うことがある
全文検索固有名詞、ID、正確なキーワード表現ゆれに弱い
ハイブリッド検索意味検索とキーワード検索の両立スコア調整やリランキングが必要
構造化DB検索権限、金額、ステータスなど正確な条件自然文から安全なクエリへ変換する必要がある

6. レイヤーごとの壊れ方

レイヤーよくある失敗対策
UI層ユーザーがAIの出力を確定結果と誤解する根拠、確認状態、未確定状態を表示する
アプリケーション層権限制御や入力検証をLLM任せにする権限、スキーマ、実行可否をコードで制御する
AI層もっともらしい誤回答を返すRAG、引用、評価、回答不能時のルールを入れる
検索層関係ない文書や古い文書を取得するメタデータ、権限フィルタ、再ランキング、鮮度管理を入れる
業務API層誤った操作を実行する確認画面、トランザクション、冪等性、監査ログを用意する
データ層権限のない情報を検索・回答に混ぜるドキュメント単位・行単位のアクセス制御を検索前に適用する
運用層品質・コスト・失敗率が見えないログ、トレース、評価データ、コスト上限、アラートを整える

7. 普通のWebアプリとの違い

普通のWebアプリAIシステム
入力はフォームやボタンで構造化される自然言語入力を解釈する必要がある
処理結果はコードで決まるLLMの非決定的な出力が混ざる
DBやAPIが主な情報源文書検索、Embedding、会話履歴も情報源になる
テストは入力と期待出力を比較しやすい評価、サンプル会話、根拠一致、失敗率を見る必要がある
ログはAPI・DB操作中心プロンプト、検索、ツール呼び出し、モデル応答も追跡対象

8. 設計チェックリスト

  • LLMに何を任せ、何を任せないかを決めたか。
  • RAGで検索する文書に権限フィルタをかけているか。
  • 検索結果の根拠や引用をUIに表示するか。
  • Tool Callingの引数をスキーマで検証しているか。
  • 重要操作の前に人間確認を入れているか。
  • 業務APIの操作は冪等性・トランザクション・監査ログを考慮しているか。
  • プロンプト、検索結果、ツール呼び出し、最終出力を追跡できるか。
  • 評価データセットを作り、モデル変更やプロンプト変更の影響を測れるか。
  • トークン利用量、検索コスト、API実行回数に上限を設けているか。
実務上の結論

AIシステムの設計では、LLMを賢い中心として扱うより、不確実な部品として扱う方が安全です。検索・権限・検証・業務実行・監査・人間確認をレイヤーごとに分けることで、壊れ方を予測しやすくなります。

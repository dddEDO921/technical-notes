OAuth 2.0を詳しく理解する

OAuth 2.0は、パスワードを第三者アプリへ渡さず、限られた権限だけを委譲するための認可フレームワークです。現在の基本形はAuthorization Code + PKCEです。

30秒でわかる答え

OAuth 2.0は「あるサービスが持つデータや機能を、別のアプリに、範囲と期限を限定して使わせる」仕組みです。ユーザーのパスワードの代わりにアクセストークンを渡すため、アプリごとに権限を制限・失効できます。

OAuth 2.0が解決する問題

たとえば写真印刷アプリに、写真サービス内の画像を読み取らせたいとします。OAuthがなければ、写真サービスのIDとパスワードを印刷アプリへ渡す設計になりかねません。

パスワードを共有する方式OAuth 2.0
第三者アプリがパスワードを保持する第三者アプリにはアクセストークンを渡す
アカウントの全権限を渡しやすい許可する操作をscopeなどで絞れる
個別アプリだけを止めにくいアプリ単位で権限を失効できる
パスワード変更まで長期間使われるトークンに短い有効期限を設定できる

重要: OAuthは認証ではなく認可

認証は「あなたは誰か」を確認すること、認可は「何をしてよいか」を決めることです。OAuth 2.0の中心は認可です。

目的代表例答える問い
認証OpenID Connect、パスキーこの利用者は誰か？
認可OAuth 2.0このアプリに何を許可するか？

「Googleでログイン」などにはOAuth 2.0を土台にしたOpenID Connect（OIDC）がよく使われます。アクセストークンだけを見てユーザー認証を実装するのではなく、ログイン目的ではOIDCのID TokenやUserInfo Endpointなどを仕様どおり利用します。

4つの登場人物

Resource Owner
権限を持つユーザー
Client
権限を使いたいアプリ
Authorization Server
許可を確認しトークンを発行

もう1つが、アクセストークンを受け取ってAPIを提供するResource Serverです。同じ事業者がAuthorization ServerとResource Serverを運営する場合もあります。

役割写真印刷アプリの例
Resource Owner写真の所有者であるユーザー
Client写真印刷アプリ
Authorization Serverログインと許可画面を提供し、トークンを発行するサーバー
Resource Server写真APIを提供するサーバー

現在の基本: Authorization Code + PKCE

ユーザーが関与するWeb・SPA・モバイルアプリでは、Authorization Code FlowにPKCEを組み合わせるのが基本です。PKCEは、認可コードを盗んだ攻撃者がアクセストークンへ交換することを防ぎます。

1. Clientが秘密値を作り
ハッシュ値を送る
2. ユーザーが
ログイン・許可
3. Clientへ短寿命の
認可コードを返す
4. Clientが認可コードと
元の秘密値を送る
5. Authorization Serverが
組み合わせを検証
6. アクセストークンで
Resource Serverを呼ぶ

1. ClientがPKCE用の値を準備

Clientは推測困難な code_verifier を生成し、そのSHA-256ハッシュから code_challenge を作ります。認可リクエストには code_challenge のみを含めます。

GET /authorize?
  response_type=code
  &client_id=photo-printer
  &redirect_uri=https%3A%2F%2Fclient.example%2Fcallback
  &scope=photos.read
  &state=random-csrf-value
  &code_challenge=hashed-verifier
  &code_challenge_method=S256

2. ユーザーが許可する

ブラウザはAuthorization Serverへ移動します。ユーザーはClientではなくAuthorization Server上でログインし、「写真の読み取りを許可しますか？」などの画面を確認します。

3. 認可コードを受け取る

許可後、Authorization Serverは事前登録されたリダイレクトURIへ短寿命・一度限りの認可コードを返します。

HTTP/1.1 302 Found
Location: https://client.example/callback?
  code=short-lived-authorization-code
  &state=random-csrf-value

4. 認可コードをトークンへ交換

Clientは認可コードと元の code_verifier をToken Endpointへ送ります。Authorization Serverはハッシュ値との対応を確認し、正しいClientだけにトークンを発行します。

POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=short-lived-authorization-code
&redirect_uri=https%3A%2F%2Fclient.example%2Fcallback
&client_id=photo-printer
&code_verifier=original-random-verifier

5. APIを呼ぶ

ClientはアクセストークンをResource Serverへ提示します。Bearerトークンの場合は通常、HTTPSのAuthorizationヘッダーで送ります。

GET /photos
Authorization: Bearer access-token-value

OAuthで扱う主な値

値役割注意点

client_secret秘密を保持できるClientの認証情報SPAやモバイルアプリ内では秘密にできない

scope要求・許可する権限範囲必要最小限にする

認可コードトークン交換用の一時的な値短寿命・一度限り
アクセストークンAPIへアクセスする権限漏えい時の影響を抑えるため短寿命・最小権限にする

アクセストークンはJWTなの？

OAuth 2.0自体は、アクセストークンの形式を決めていません。JWTの場合も、意味を読み取れないランダム文字列（opaque token）の場合もあります。

形式Resource Serverでの検証例特徴
JWT署名、有効期限、発行者、audienceなどを検証サーバー単独で検証しやすいが、失効や情報露出に注意
Opaque tokenAuthorization Serverへ問い合わせる、または共有ストレージを参照中身を外部へ見せず、中央で状態管理しやすい

Clientはアクセストークンの中身に依存せず、APIへ渡す値として扱うのが基本です。

Clientの種類と秘密の扱い

OAuth 2.0では、Clientが認証情報を安全に保持できるかが重要です。

  • Confidential Client: バックエンドサーバーなど、秘密を保持できるClient。
  • Public Client: SPA、モバイル、デスクトップアプリなど、配布物から秘密を取り出せるClient。

Public Clientへ埋め込んだ client_secret は秘密ではありません。PKCEはそのようなClientでも認可コードの横取りを防ぐために設計され、現在の推奨ではWebアプリを含むすべての種類のClientへ適用されます。

現在のセキュリティ基本方針

RFC 6749は2012年公開ですが、脅威と推奨事項は2025年公開のRFC 9700で更新されています。2026-06-10時点で、実装時には両方を参照する必要があります。

  • Authorization Code + PKCEを利用し、PKCEは S256 を使う。
  • Implicit Grantは避け、アクセストークンを認可レスポンスやURLへ露出させない。
  • Resource Owner Password Credentials Grantは使用しない。
  • リダイレクトURIを事前登録し、完全一致で検証する。
  • Authorization Server、Client、Resource Server間をHTTPSで通信する。
  • アクセストークンのscope、対象Resource Server、有効期限を最小化する。
  • Public Clientのリフレッシュトークンは、送信者制約またはローテーションでリプレイを検知する。
  • トークン、認可コード、Clientの秘密情報をログやURLへ残さない。
  • 実績のあるOAuth/OIDCライブラリを利用し、独自実装を避ける。

よくある誤解

誤解実際
OAuthはログイン方式であるOAuthは認可の枠組み。ログインには通常OIDCを組み合わせる
アクセストークンは必ずJWTである形式はOAuth仕様で決められていない
JWTなら安全である署名検証、issuer、audience、期限などの検証と安全な保管が必要
SPAへclient_secretを埋め込めば安全になる配布されたコードから取得できるため秘密として扱えない
長いscopeを要求しておけば便利漏えい時の被害が増えるため必要最小限にする
設計時の判断軸

「誰の権限で」「どのClientが」「どのResource Serverの」「どの操作を」「いつまで許可されるか」を分けて考えると、OAuth 2.0の設計が整理しやすくなります。

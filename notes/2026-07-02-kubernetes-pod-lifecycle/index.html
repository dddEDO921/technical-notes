Kubernetes Podライフサイクルを実務目線で理解する

Podの状態を見るときは、Pod全体のphaseと、Pod内のコンテナ状態を分けて読む。CrashLoopBackOffなどのSTATUS表示も、この2層を分けると落ち着いて調査できます。

30秒でわかる答え

Podは作成されるとPendingから始まり、スケジューリング、イメージ取得、コンテナ起動を経てRunningになります。処理が正常終了すればSucceeded、失敗終了すればFailedです。ただし実務でよく見るCrashLoopBackOffやImagePullBackOffはPod phaseではなく、コンテナ状態や待機理由をkubectlが見やすく表示したものです。

まず2層で見る

Podライフサイクルは、Podオブジェクト全体の状態と、Pod内のコンテナ状態を分けると理解しやすくなります。Deploymentなどに管理されている場合、Podそのものが別Nodeへ移動して復活するのではなく、必要に応じて新しいPodが作られます。

Pod phaseの意味

phase意味よく見る場面
PendingPodは作成済みだが、まだ全コンテナが起動していない。スケジューリング待ち、イメージ取得中、ボリューム待ち。
RunningPodがNodeに割り当てられ、少なくとも1つのコンテナが起動中または起動・再起動中。通常稼働中。中のコンテナが再起動中でもRunningに見えることがある。
Succeededすべてのコンテナが正常終了し、再起動されない。Jobや一回だけ実行する処理。
Failedすべてのコンテナが終了し、少なくとも1つが失敗終了した。Job失敗、restartPolicy: NeverのPod失敗。
UnknownPod状態を取得できない。Node障害、kubeletとの通信断。

STATUSはphaseと同じとは限らない

kubectl get podのSTATUS列には、Pod phaseだけでなく、コンテナの待機理由や終了理由が表示されることがあります。そのため、CrashLoopBackOffを「Pod phaseの一種」と覚えると混乱します。

STATUS表示正体まず見るところ
CrashLoopBackOffコンテナが起動後すぐ終了し、再起動間隔が伸びている。kubectl logs --previous、終了コード、アプリ設定。
ImagePullBackOffイメージ取得に失敗し、再試行待ち。イメージ名、タグ、registry認証、ネットワーク。
ErrImagePullイメージ取得でエラーが出た直後。kubectl describe podのEvents。
TerminatingPod削除要求を受け、終了猶予期間中。preStop、SIGTERM処理、finalizer。

restartPolicyで何が再起動するか

restartPolicyは、Pod内のコンテナを再起動するかを決めます。Deploymentのような長期稼働ワークロードでは通常Alwaysです。一方、Pod自体が消えた場合は、DeploymentやReplicaSetなどのControllerが必要数を満たすために新しいPodを作ります。

restartPolicy動き主な用途
Alwaysコンテナが終了したら再起動する。Deployment、DaemonSetなど。
OnFailure失敗終了した場合だけ再起動する。Jobなど。
Never終了しても再起動しない。一回限りの検証Podなど。
言い換えのコツ

「Podが再起動した」と言いたくなる場面でも、実際には「同じPod内のコンテナが再起動した」のか、「Controllerが別のPodを作り直した」のかを分けて確認します。

Probeはライフサイクルにどう効くか

Probeは、コンテナが起動したあとにKubernetesがアプリケーションの状態を判断する仕組みです。特にreadinessProbeとlivenessProbeを混同すると、不要な再起動や一時障害の拡大につながります。

Probe役割失敗したとき
startupProbe起動に時間がかかるアプリを待つ。失敗が続くとコンテナは再起動される。
livenessProbeアプリが生きているかを見る。失敗するとkubeletがコンテナを再起動する。
readinessProbeリクエストを受けてよいかを見る。Serviceの宛先から外れるが、通常それだけでは再起動しない。

終了処理の流れ

Podが削除されると、すぐにプロセスが殺されるわけではありません。Kubernetesは猶予期間を設け、アプリケーションが正常終了できるようにします。

調査するときの最短ルート

# 一覧でSTATUS、READY、RESTARTSを見る
kubectl get pod

# 詳細。Events、Conditions、コンテナ状態、終了理由を見る
kubectl describe pod <pod-name>

# 現在のログを見る
kubectl logs <pod-name> -c <container-name>

# 直前に落ちたコンテナのログを見る
kubectl logs <pod-name> -c <container-name> --previous

# Pod phaseだけを確認する
kubectl get pod <pod-name> -o jsonpath='{.status.phase}'

よくある誤解

  • CrashLoopBackOffはPod phaseではなく、コンテナ再起動の待機状態を示す表示です。
  • PodがRunningでも、アプリがリクエストを受けられるとは限りません。受けられるかは主にreadinessProbeで判断します。
  • livenessProbeは「依存先に接続できるか」ではなく「このプロセスを再起動すべきほど壊れているか」を見る用途に寄せます。
  • Podは基本的に特定Nodeに割り当てられた使い捨ての実行単位です。Nodeをまたいで同じPodが移動する、と考えない方が正確です。
  • Deploymentがある場合、壊れたPodを修理するのではなく、望ましいReplica数に戻すために新しいPodを作ります。
理解の要点

Podライフサイクルの読み方は、phase、コンテナ状態、Controllerの動きの3つを分けることです。STATUS列だけで判断せず、describe、Events、logs --previousまで見ると原因に近づけます。

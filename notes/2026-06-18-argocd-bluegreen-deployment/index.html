Argo CDのBlue-GreenデプロイをKubernetes用語で理解する

Argo CDでBlue-Greenデプロイを行うときの実体は、多くの場合Argo Rolloutsです。KubernetesのService、ReplicaSet、Pod、selectorの切り替えとして理解すると分かりやすい。

30秒でわかる答え

Blue-Greenデプロイは、旧バージョンのPod群と新バージョンのPod群を並べておき、Serviceのselectorを旧ReplicaSetから新ReplicaSetへ切り替える方式です。Argo RolloutsではactiveServiceが本番トラフィック、previewServiceが新バージョン確認用の入口になります。

Argo CDだけでやるのか？

Argo CDはGitの状態をKubernetesへ同期するGitOpsツールです。Blue-GreenやCanaryのような段階的デプロイを制御する場合は、同じArgoプロジェクトのArgo Rolloutsを組み合わせるのが一般的です。

ツール役割
Argo CDGitにあるRollout、Service、IngressなどのManifestをクラスタへ同期する
Argo RolloutsRolloutリソースを監視し、Blue-GreenやCanaryの進行、Service selectorの切り替え、Analysisを制御する
KubernetesReplicaSet、Pod、Service、Ingressなどを実際に動かす

Kubernetes用語で見る全体像

通常のDeploymentでは、KubernetesのDeployment ControllerがReplicaSetを作ります。Argo Rolloutsでは、Deploymentの代わりにRolloutリソースを使い、Rollout ControllerがReplicaSetを管理します。

Blue-Greenの流れ

  1. 安定状態では、activeServiceが旧ReplicaSet v1のPodへトラフィックを流している。
  2. GitでRolloutのPod template、たとえばimage tagをv2へ更新する。
  3. Argo CDがGitの変更をクラスタへ同期する。
  4. Argo Rollouts Controllerが新しいReplicaSet v2を作る。
  5. previewServiceのselectorがReplicaSet v2のPodへ向く。
  6. 新PodがReadyになるまで待つ。
  7. 必要ならprePromotionAnalysisでメトリクスやJobを確認する。
  8. 手動または自動でPromoteする。
  9. activeServiceのselectorがv1からv2へ切り替わる。
  10. 必要ならpostPromotionAnalysisを実行する。
  11. scaleDownDelaySeconds後に旧ReplicaSet v1を縮退する。

最小イメージのManifest

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: sample-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-api
  template:
    metadata:
      labels:
        app: sample-api
    spec:
      containers:
        - name: sample-api
          image: example/sample-api:v2
          ports:
            - containerPort: 8080
  strategy:
    blueGreen:
      activeService: sample-api-active
      previewService: sample-api-preview
      autoPromotionEnabled: false
      scaleDownDelaySeconds: 60
apiVersion: v1
kind: Service
metadata:
  name: sample-api-active
spec:
  selector:
    app: sample-api
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: sample-api-preview
spec:
  selector:
    app: sample-api
  ports:
    - port: 80
      targetPort: 8080

実際にはArgo Rollouts ControllerがReplicaSetごとの一意なhash labelをService selectorへ注入し、activeServiceとpreviewServiceがどのReplicaSetへ向くかを制御します。

Canaryとの違い

観点Blue-GreenCanary
トラフィックある時点で旧から新へ切り替える10%、30%、50%のように段階的に流す
必要リソース旧・新を並べるので一時的に多い段階配分により調整しやすい

注意点

  • Blue-GreenはPodを2系統持つため、一時的にリソースを多く使う。
  • DB migrationに後方互換性がないと、旧Podと新Podの並存中に壊れる。
  • Serviceのselector切り替えにはiptablesなどの反映遅延があるため、旧ReplicaSetをすぐ落とさない。
  • Argo RolloutsではscaleDownDelaySecondsで旧ReplicaSetの縮退を遅らせる。
  • AWS ALB IngressではBlue-Green時に安全に切り替えられず、ダウンタイムリスクがあると公式ドキュメントで注意されている。
  • Promote前に確認したいならautoPromotionEnabled: falseを使う。
  • メトリクスで自動判定したいならprePromotionAnalysisやpostPromotionAnalysisを使う。

実務チェックリスト

  • activeServiceとpreviewServiceの用途をチームで理解しているか。
  • Ingressや他サービスはactiveServiceを見ているか。
  • Promoteを手動にするか自動にするか決めているか。
  • previewServiceで何を確認するか決めているか。
  • DB migrationは旧Pod・新Podの両方と互換性があるか。
  • 旧ReplicaSetをどれくらい残すか決めているか。
  • rollback手順をkubectl argo rolloutsまたは運用Runbookに書いているか。
  • メトリクス、ログ、アラートで切り替え後の異常を検知できるか。
理解の要点

Argo RolloutsのBlue-Greenは、Kubernetes的には「新しいReplicaSetを先に作り、Serviceのselectorを旧ReplicaSetから新ReplicaSetへ切り替える仕組み」です。Argo CDはそのManifestをGitから同期し、Rollouts Controllerが実際の切り替えを制御します。

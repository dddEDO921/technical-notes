# Write Technical Note

1. 最初の `質問:` だけでノート本文を作らない。まず方向性確認を行う。
2. 方向性確認では、仮タイトル、想定読者、扱う範囲、扱わない範囲、予定構成、確認したい論点を短く提示する。想定読者は、明示がない限りユーザー本人とする。
3. 必要に応じて、記事の深さ、対象読者、実務例の有無、比較対象、図解の必要性などを決める質問を1〜3個だけ行う。
4. ユーザーが方向性に合意するか、十分に具体的な追加指示を出すまでは、調査の深掘り、HTML作成、`data/index-items.json` 更新、commit / push を行わない。
5. 合意後、質問の論点を1つの短いタイトルに整理する。
6. 変化しうる情報や不確かな技術事項は調査する。公式文書、標準仕様、原論文を優先する。
7. `notes/<yyyy-mm-dd>-<short-slug>/index.html` を作る。既存ノートの構造と `styles/site.css` を再利用する。
8. 次の順序を基本に、質問に合う構成へ調整する。
   - 30秒でわかる答え
   - 全体像または処理フロー
   - 仕組みの詳細
   - 具体例
   - 注意点・適用しない場面
   - 参照元
9. 図解は HTML/CSS、表、コード、またはインライン SVG で作る。装飾目的だけの図は不要。
10. 読者が結論と根拠を区別できるように書く。不確かな点、前提、調査日を明示する。
11. 参照元にはページ名、提供元、URL、確認日を記載する。
12. `data/index-items.json` の共通知識インデックスに新しい解説ノート項目を追加する。`kind`、`href`、`title`、`category`、`categoryLabel`、`summary`、`date`、`keywords` を設定する。
13. 相対リンクと表示を検証する。
14. `AGENTS.md` の Publish flow に従い、対象ファイルだけを commit して `main` へ push する。検証で問題がある場合や作業対象外の差分を切り分けられない場合は push しない。

秘密情報、個人情報、ローカル環境固有の値は含めない。`.codex-remote-attachments/` などユーザー添付由来の未追跡ファイルは commit しない。
